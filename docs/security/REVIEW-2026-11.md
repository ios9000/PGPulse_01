## How the claims were checked

- **Code reading** of every file listed in each section.
- **Live PostgreSQL 16** (throwaway local cluster). Used to confirm three claims:
  1. `SET LOCAL default_transaction_read_only = ON` inside an open transaction leaves `transaction_read_only = off`.
  2. A "diagnostic" playbook transaction that is then rolled back can still terminate another role's session.
  3. `EXPLAIN (FORMAT JSON, ANALYZE) DELETE …` deletes rows.
  The same cluster also showed that a `pg_monitor` member can read `primary_conninfo` (password included) from `pg_settings`.
- **pgx PoC** (pgx v5.8.0, a copy of `substituteDBName`). Used to confirm that a database name containing ` host=…` sends a connection, with the stored password, to another host.
- **`govulncheck`** against the Go vulnerability DB. `vuln.go.dev` is blocked by this environment's network policy, so the scan used its backing store `-db https://storage.googleapis.com/go-vulndb`.
- **`npm audit`** in `web/`, run once in full and once with `--omit=dev`.

## Severity scale

| Severity | Meaning |
|---|---|
| Critical | Unauthenticated, or lowest-role, compromise of PGPulse or of the monitored databases. |
| High | A privilege boundary is crossed, credentials leak, or the database is modified without the controls the design calls for. |
| Medium | Needs a privileged role or an unusual setup, or causes DoS or weaker auditing. |
| Low | Hardening, defence in depth, or a latent problem. |

## 1. Authentication and sessions

### 1.1 Critical — Auth is off by default, binds all interfaces, and the documented localhost restriction is not implemented

**Where**
- `internal/config/load.go:269-272`: `validateAuth` returns early when `!cfg.Auth.Enabled`. The Go zero value is `false`, so a config without an `auth:` block has auth disabled.
- `pgpulse.yml:23` and `configs/pgpulse.example.yml:23`: `auth.enabled: false`. The comment at `pgpulse.yml:20` says "When disabled (default), all API endpoints are open".
- `cmd/pgpulse-server/main.go:85-88`: with `--target` and no config file, `cfg = config.Config{}`, so auth is always off.
- `cmd/pgpulse-server/main.go:100-102` and `main.go:130-132`: `--no-auth` forces `AuthDisabled` even when the config enables auth.
- `cmd/pgpulse-server/main.go:109-111`: listen address defaults to `:8989` on all interfaces. `internal/config/load.go:60` falls back to `:8080`, also all interfaces.
- `internal/auth/middleware.go:32-49`: in `AuthDisabled` mode every request gets `Role: super_admin` claims.
- `internal/api/server.go:377-526`: the auth-disabled route group exposes every route. This includes session terminate (`:438`), EXPLAIN (`:441`), instance create/update/delete/test (`:519-523`), alert rule CRUD (`:448-451`), and every playbook mutation and execution (`:478-501`).

**Design versus code.** `docs/HANDOFF_MW_01_to_next.md:28` and `:60` describe the bypass as "auto-enabled on localhost; `--no-auth` flag for remote bind". There is no loopback check anywhere in `cmd/` or `internal/`. The only `localhost` comparisons are in `internal/collector/os.go:85-91` (OS-metrics source) and the CORS default.

**Impact.** Anyone who can reach port 8989 or 8080 gets super_admin. They can:
- terminate sessions on monitored databases;
- run arbitrary DML through EXPLAIN ANALYZE (see 3.2);
- add an instance with their own DSN, or redirect an existing one;
- run playbook steps.

All of this is done as the monitoring role.

**Reproduction** (quick-start mode on a network-reachable host):
```bash
pgpulse-server --target 'postgres://pgpulse_monitor:pw@db:5432/postgres'
```
```bash
curl -s -X POST http://victim:8989/api/v1/instances/cli-target/explain \
  -H 'Content-Type: application/json' \
  -d '{"database":"postgres","query":"DELETE FROM important_table","analyze":true}'
```
`cli-target` is the fixed instance ID from `main.go:732`. No token is needed.

**Fix**
- Fail closed: make auth enabled unless explicitly disabled.
- When auth is disabled, refuse to bind anything except `127.0.0.1` or `::1`, unless a second explicit flag such as `--i-know-auth-is-off` is given.
- Default the listen address to `127.0.0.1:8989` in quick-start mode.

### 1.2 High — The example JWT secret is accepted as valid

**Where**
- `pgpulse.yml:24` and `configs/pgpulse.example.yml:24`: `jwt_secret: "change-me-to-at-least-32-characters-long"` (41 characters).
- `internal/config/load.go:276`: the only check is `len >= 32`.
- `pgpulse.yml:31`: initial admin password `"changeme"`.

**Impact.** An operator who sets `auth.enabled: true` and changes nothing else runs with a publicly known HMAC key. Anyone can mint `{"type":"access","role":"super_admin"}` tokens. `RequireAuth` only checks the signature and the `type` claim (`internal/auth/middleware.go:70-79`).

**Reproduction.** Sign `{"iss":"pgpulse","uid":1,"usr":"x","role":"super_admin","type":"access","exp":<now+3600>}` with HS256 and that string. Then:
```bash
curl -H "Authorization: Bearer $TOKEN" http://host:8080/api/v1/auth/users
```

**Fix.** Reject known placeholder secrets and require high entropy, for example 32 random bytes in base64. Ship the example with an empty `jwt_secret` and generate one on first start. Refuse to start when the initial admin password is `changeme` or `CHANGE_ME`.

### 1.3 High — The login rate limiter can be bypassed and its memory grows without bound

**Where**
- `internal/auth/ratelimit.go:83-89`: `ClientIP` trusts `X-Forwarded-For`, then `X-Real-IP`, from any client. There is no trusted-proxy list.
- `internal/api/server.go:543`: the limiter is keyed on that value.
- `internal/auth/ratelimit.go:39-44`: `RecordFailure` appends to a per-key slice.
- `internal/auth/ratelimit.go:66-79`: `pruneExpired` only runs for the key being queried. Keys an attacker never revisits are never removed.

**Impact.**
- Unlimited online password guessing: send a new `X-Forwarded-For` on every request. Combined with the default `admin`/`changeme` (1.2), this is the realistic way into an auth-enabled deployment.
- The same trick grows the map by one entry per request, which is a slow memory DoS.
- There is no per-username lockout.

**Reproduction**
```bash
for i in $(seq 1 1000); do
  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "X-Forwarded-For: 10.$((i/65536)).$((i/256%256)).$((i%256))" \
    -d '{"username":"admin","password":"guess'$i'"}' \
    http://host:8080/api/v1/auth/login
done | sort | uniq -c
```
Expected: 1000 × `401` and no `429`.

**Fix**
- Use `r.RemoteAddr` unless the peer is in a configured `trusted_proxies` list.
- Also limit per username.
- Add a periodic sweep of expired keys and a hard cap on map size.

### 1.4 Medium — No revocation, no refresh rotation, and access tokens accepted as refresh tokens

**Where**
- `internal/auth/middleware.go:55-85`: `RequireAuth` never checks the database. Deactivating, deleting, changing the role of, or resetting the password of a user does not affect tokens already issued. Access tokens last 24 h (`internal/config/load.go:279-281`). The role inside the token keeps working until it expires.
- `internal/api/auth.go:139-174`: refresh issues a new access token but never rotates or invalidates the refresh token. A stolen refresh token works for 7 days, even after a password change (`auth.go:381-415` does not invalidate anything).
- `internal/auth/jwt.go:125-141`: `ValidateRefreshToken` does not check `claims.Type == TokenRefresh`.
- `cmd/pgpulse-server/main.go:464-467`: `refresh_secret` defaults to `jwt_secret`, and the shipped config leaves it empty (`pgpulse.yml:25`). So an **access** token is accepted by `/auth/refresh`. A stolen 24 h token can be turned into new tokens for as long as the user stays active.

**Reproduction**
```bash
curl -X POST /api/v1/auth/refresh -d '{"refresh_token":"<ACCESS TOKEN>"}'
```
Returns a fresh `access_token`.

**Fix**
- Check `Type` in `ValidateRefreshToken`.
- Require a distinct `refresh_secret`.
- Add a per-user `token_version` (or `password_changed_at`) column. Embed it in tokens and compare it in `RequireAuth` (one cached lookup) and in `/auth/refresh`.
- Rotate refresh tokens on use.

### 1.5 Low — JWT algorithm not pinned; `iss` and `exp` not required

`internal/auth/jwt.go:106-111` and `:126-131` accept any `*jwt.SigningMethodHMAC` (HS256, HS384 or HS512). There are no `jwt.WithValidMethods([]string{"HS256"})`, `jwt.WithIssuer("pgpulse")` or `jwt.WithExpirationRequired()` options. Exploiting this needs the secret, but a token minted without `exp` would never expire.

**Fix:** pass all three parser options.

### 1.6 Low — bcrypt cost unbounded; no password policy; username-enumeration timing

- `internal/config/load.go:285-287` defaults the cost to 12 but accepts any value. A cost of 4 is weak. A cost of 20 or more makes each login take minutes, so a few requests are a CPU DoS. Clamp it to 10–14.
- `internal/api/auth.go:217-220` (register) and `auth.go:387-390` (change password) accept a 1-character password. Only the admin reset (`auth.go:353`) enforces 8 characters.
- `internal/api/auth.go:89-97`: an unknown username returns without running bcrypt. A known username costs about 250 ms at cost 12. That timing difference reveals valid usernames. Compare against a dummy hash on the not-found path.

### 1.7 Low — `RequireRole` ignores its argument

`internal/auth/middleware.go:89-106`: `RequireRole(requiredRole, …)` only checks `PermViewAll`, which every role has (`internal/auth/rbac.go:29-34`). It is unused today. The first route that uses it would be open to every role. Delete it or implement it.

### 1.8 Low — Credentials on the command line; `sslmode=disable` hard-coded

- `cmd/pgpulse-server/main.go:46`: `--target-password` puts the password in `ps` output and shell history.
- `cmd/pgpulse-server/main.go:714-715`: the synthesized DSN forces `sslmode=disable`, so the password and all traffic cross the network in clear text.

**Fix:** read the password from `PGPASSWORD` or a file, and default to `sslmode=prefer` or `require`.

### 2.1 Critical — `roles_admin` can take over `super_admin` (and lock everyone out)

**Where**
- `internal/api/auth.go:339-379` (`handleAdminResetPassword`): checks that the target exists (`:358`) but never checks the target's role. A roles_admin can reset any super_admin's password.
- `internal/api/auth.go:270-282` (`handleUpdateUser`): only stops a non-super_admin from **assigning** `super_admin` or `roles_admin`. It does not stop them **modifying a user who already is** super_admin. A roles_admin can demote every super_admin to `app_admin`, or set `active:false` on them.
- `auth.go:283`: no "last active super_admin" check on update. The check exists only in delete (`auth.go:319-329`).
- `internal/api/auth.go:319-329` (`handleDeleteUser`): a roles_admin may delete super_admins as long as more than one exists.

**Reproduction** (as roles_admin, with the super_admin at id=1):
```bash
curl -X PUT -H "Authorization: Bearer $ROLES_ADMIN" \
  -d '{"new_password":"pwned-12345"}' \
  http://host:8080/api/v1/auth/users/1/password
```
```bash
curl -d '{"username":"admin","password":"pwned-12345"}' \
  http://host:8080/api/v1/auth/login
```
The second call returns super_admin tokens. Alternatively, `PUT /auth/users/1 {"active":false}` for every super_admin leaves the deployment with no super_admin and no way to recover through the API.

**Fix.** A caller who is not super_admin must not reset, update, deactivate or delete a user whose current role is `super_admin` or `roles_admin`. Enforce "at least one active super_admin" in `Update` (role change and deactivation) as well as in `Delete`. Do this inside a transaction so two concurrent requests cannot both pass the check.

### 2.2 High — Remediate-tier confirmation is client-side only; `/confirm` and `/approve` are no-ops

**Where**
- `internal/api/playbooks.go:361-373`: a `remediate` step runs for **any** authenticated role if the body contains `{"confirmed":true}`. There is no permission check.
- `internal/api/playbooks.go:478-481`: `handleConfirmStep` returns `{"status":"confirmed"}` and does nothing else. Its route has instance_mgmt (`server.go:335`), but `/execute` does not depend on it.
- `internal/api/playbooks.go:483-495`: `handleApproveStep` calls `ResetStepForRetry`. That only changes rows with `status = 'failed'` (`internal/playbook/pgstore.go:529-533`), so for a `pending_approval` step it is a no-op.
- `internal/api/playbooks.go:374-381`: a dangerous-tier step runs if and only if the **caller** has instance_mgmt. No approval record is ever consulted.

**Impact.**
- app_admin and roles_admin users can run every remediate step.
- The "DBA approves" flow advertised at `playbooks.go:512` does not exist: a requester cannot be approved, and a dba never needs approval.
- Neither the request nor the approval is recorded with a user.

**Reproduction** (as app_admin):
```bash
curl -X POST -H "Authorization: Bearer $APP_ADMIN" -d '{"confirmed":true}' \
  /api/v1/playbook-runs/$RUN/steps/$N/execute
```

**Fix**
- Record confirmations and approvals in `playbook_run_steps`: who, when, and a hash of the SQL.
- Make `/execute` require that record for tiers 2 and 3.
- Gate tier 2 on instance_mgmt.
- For tier 3, require approver ≠ requester.

### 2.3 Low — No ownership checks on runs

`internal/api/playbooks.go:533-550` (skip), `:553-576` (abandon) and `:517-530` (retry) act on any `runId` from any user. A user can disrupt another user's incident response.

### 2.4 Low — `is_builtin` and `requires_permission` are trusted from the request body

- `internal/api/playbooks.go:68-79` decodes the whole `Playbook` from JSON. `internal/playbook/pgstore.go:39-43` stores `pb.IsBuiltin` as sent, so an app_admin can create playbooks that the delete handler (`playbooks.go:137-140`) refuses to remove.
- `RequiresPermission` is stored (`pgstore.go:43`, `:136`) but never enforced anywhere.

### 2.5 Low — Raw query text visible to every role

`GET /instances/{id}/activity/long-transactions`, `/activity/locks` and `/snapshots` (`server.go:210-235`) return `pg_stat_activity.query` and `pg_stat_statements` text to app_admin and roles_admin. That text can contain literals such as PII, or `ALTER ROLE … PASSWORD '…'` while it is running. Consider instance_mgmt for raw text, or redacting literals.
